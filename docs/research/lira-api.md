# Исследование: API ЛИРА-САПР

Дата: 2026-10-27. Источники: библиотеки типов установленной ЛИРА-САПР 2024 R2 (Update R2.3),
документация на rflira.ru и lira.land, релиз-ноты.

## Готовые MCP-серверы

Публичных MCP-серверов для ЛИРА-САПР / ЛИРА-САПФИР не найдено: ни на GitHub, ни в
каталогах MCP, ни у разработчика. Python-обёрток над API тоже не найдено.

## Какие программные интерфейсы есть

ЛИРА-САПР предоставляет три независимых COM-интерфейса. COM (Component Object Model) — механизм
Windows, через который одна программа вызывает объекты другой; из Python он доступен через
библиотеки `pywin32` или `comtypes`.

| Интерфейс | Где живёт | ProgID / библиотека типов | Назначение |
|---|---|---|---|
| ЛИРА-САПР API (ВИЗОР) | `Bin\x64\LiraSapr.exe`, отдельный процесс | `LiraSapr.Application` (2024); в 2025 — `LiraSapphire.Application` | Открыть/создать/сохранить модель, таблицы ввода, выделение, запуск расчёта, CSV-результаты, импорт файлов |
| RES API (результаты) | `Bin\x64\LiraResAPI.dll`, загружается в процесс клиента | `LiraSaprRes` | Чтение результатов расчёта: перемещения, усилия, РСУ, РСН, периоды колебаний, подобранная арматура, нагрузки на фрагмент, продавливание |
| САПФИР API | `Sapfir 2024\SAPFIR.tlb` | `Sapfir.Application.2024.0` | Архитектурная (BIM) модель: стены, плиты, колонны, этажи, оси; около 50 объектов автоматизации |

Полные выгрузки библиотек типов: [LiraSapr-2024R2.txt](typelib/LiraSapr-2024R2.txt),
[LiraResAPI-2024R2.txt](typelib/LiraResAPI-2024R2.txt).

## Что умеет ЛИРА-САПР API 2024 R2

- **Приложение**: `OpenDocument`, `CreateNewDocument`, `ImportFile` (импорт файла с шаблоном модели),
  `StartAnalysis` (асинхронно, события `AnalysisStarting/Finished/Stopped`),
  `StartAnalysisOnServer`, `StopAnalysis`, `DeleteResults`, `StartZip/StartUnzip` (архивы),
  `StartCmd` (любая команда меню по идентификатору), единицы измерения.
- **Документ**: `Save/SaveAs/Close`, выделение узлов и элементов, текущее загружение,
  собственный вес (`SetDeadWeightLoad`), модель грунта (`SetSoilModel`),
  генерация CSV-таблиц результатов при расчёте (`SetGenerateCsvTables`, около 80 видов таблиц).
- **Таблицы ввода** (чтение и запись двумерным массивом, `Apply` возвращает ошибки по строкам):
  координаты узлов, элементы (тип и узлы), связи, жёсткости и их назначение, коэффициенты постели C1/C2,
  жёсткие вставки, шарниры, объединение перемещений, локальные оси, монтажные стадии,
  РСН, загружения, массы, координационные оси, высотные отметки, конструктивные блоки,
  материалы конструирования.

## Пробелы и риски

- **Нет таблицы ввода нагрузок** на узлы и элементы. Решено (T2): импорт текстового
  формата ЛИРА через `ImportFile`.
- **РСУ** (расчётные сочетания усилий) отдельной таблицы ввода не имеют. Решено (T2):
  виды загружений и коэффициенты РСУ — документ 8 текстового формата.
- Многие методы могут показывать диалоги ("Messages from UI can be shown"); модальное окно
  остановит автоматизацию. Нужна стратегия: тайм-ауты, обнаружение зависания.
- ProgID и имя библиотеки типов сменились между 2024 и 2025 (`LiraSapr` → `LiraSapphire`).
- Нужна лицензия (ключ Guardant) и запущенный графический интерфейс ЛИРА; одна машина Windows.
- Документация методов — только описания внутри библиотеки типов; формат параметров таблиц
  нужно изучать, заполняя таблицы вручную в интерфейсе.

## Эксперимент T2 на живой ЛИРЕ 2024 R2.3 (2026-10-27)

Скрипты — папка `spikes/` (`t2_*.py`). Всё проверено из Python через pywin32.

**Работает:**

- Подключение `gencache.EnsureDispatch("LiraSapr.Application")` запускает `LiraSapr.exe` с
  окном. `CreateNewDocument` создаёт модель в папке Data ЛИРЫ; `SaveAs` переносит её
  в любую папку.
- Таблицы ввода: `CreateNewItem(тип, None, kLiraModelPart_All, имя, -1)` → `CastTo(...,
  "ILiraTable")`. `SetContents` принимает и текст с табуляциями, и список списков Python;
  `Apply()` возвращает `(успех, ошибки)`. `GetContents("")` на пустой таблице узлов или
  элементов падает с ошибкой — сначала проверять наличие данных.
- Форматы таблиц (по учебной модели): жёсткость — строка параметров сечения
  (`Ro:0 E:3e+006 B:60 H:40 … STD_END`); связи — номер узла и 6 флагов; загружения и
  РСН — таблицы с видом загружения текстом («Постоянное(П)»). Полная выгрузка —
  `spikes/out/*.tables.txt` (не в git).
- **Импорт текстового формата ЛИРЫ** `app.ImportFile(путь.txt, "")` создаёт новую модель с
  узлами, элементами, жёсткостями, связями, загружениями **и нагрузками** (документы 6 и 7).
- **Выгрузка в текстовый формат:** `app.StartCmd(5049)` («Создать текстовый файл» из меню)
  без диалога пишет `<папка Data ЛИРЫ>\<имя модели>.txt` в UTF-8; команда асинхронна —
  ждать появления файла. В файле есть нагрузки (6, 7) и настройки РСУ (8).
- **Расчёт:** `StartAnalysis(путь.lir)` возвращается сразу; события через
  `win32com.client.WithEvents` приходят при прокачке сообщений
  (`pythoncom.PumpWaitingMessages`): `AnalysisStarting(0)`, `(1001)`, `AnalysisFinished(0)`.
- **Результаты:** `Dispatch("{4F4546AE-AC54-48A2-9414-1B9EF6519A37}")` (LiraResultsAccess,
  ProgID нет) → запрос `kLiraRequest_LoadCaseForces`, `DocumentName` = имя модели без пути.
  Индексы: сечение с 1, загружение с 1, форма для статики = 1, история = 0. Единицы
  фиксированы: т, т·м.
- **Проверка числом:** рама 6×3 м, защемление, 10 т/м на ригель (40×60, E=3e6):
  M на концах ригеля −23,858 т·м, в пролёте 21,142, у основания стоек 11,575, N стоек 30 т.
  Ручной расчёт без сдвига: 24 / 21 / 12 / 30.

**Ограничения и риски:**

- Таблицы нагрузок в API нет. Новые модели — через генерацию текстового формата и
  `ImportFile`. Существующие модели — круг «выгрузка 5049 → правка → импорт» **с потерями**:
  виды загружений «Мгновенное» становятся «Особое» (меняются коэффициенты сочетаний),
  теряются конструктивные блоки. Нужна схема «импорт + восстановление таблиц из
  оригинала + сверка» (решается в T6).
- Результаты пишутся в папку Work ЛИРЫ под **именем модели**: модели с одинаковым именем
  из разных папок перезаписывают результаты друг друга.
- Выгрузка 5049 пишет в папку Data ЛИРЫ под именем модели — может перезаписать чужой
  файл с тем же именем.
- `SaveAs` с расширением `.txt` пишет двоичный `.lir`, а не текст.
- ЛИРА сама делает копии `*_Backup*.~lir` рядом с моделью при сохранении.
- Описания методов в библиотеке типов обрезаны до 255 символов.

## Находки T6 (2026-10-27)

- Папки ЛИРЫ — в реестре `HKCU\Software\LIRA SAPR\LIRA SAPR 2024\Directories`:
  `DataDirectory`, `TextDataDirectory`, `WorkDirectory`, `ResultDirectory`.
- Любое чтение таблицы (создание и удаление временной таблицы ввода) выставляет у модели
  флаг «изменена». Адаптер помнит модели, изменённые только своими чтениями, и не считает
  их изменёнными.
- При выгрузке ЛИРА дополняет строки значений нагрузок нулями до 4 значений.
- **Импорт текстового формата переключает модель на нормы сочетаний по умолчанию**
  (СП 20.13330) и путает виды загружений даже у моделей с этими нормами. Запись строк
  `LoadCases` возвращает виды, только если они есть в словаре норм по умолчанию: ЛИРА
  переводит значения в этот словарь. Поэтому правка нагрузок существующих моделей
  работает для моделей с нормами по умолчанию; для остальных сервер отказывается и
  оставляет модель нетронутой (уточнено 2026-10-29, см. «Находки T25»).
- COM-объекты нельзя держать в циклических ссылках и в трассировках исключений, которые
  уходят из COM-потока: сборщик мусора освободит их в другом потоке
  (`0x800401f0 CO_E_NOTINITIALIZED`).

## Находки T25: нормы сочетаний (2026-10-28)

Пробы `spikes/t25_template.py`, `t25_params.py`, `t25_strip.py` на примере №1 (виды
загружений «Постоянное(П)», «Длительное(Д)», «Мгновенное(М)»).

- В тексте нормы не записаны: документ 8 (РСН) хранит виды загружений числовыми кодами,
  и при импорте ЛИРА читает код 7 по своим нормам по умолчанию как «Особое ( Ps)».
- Справка ЛИРЫ (`Bin\help\ru\LiraSapr.chm`, страница «Импортировать задачу из текстового
  файла по разделам») перечисляет разделы текста: нормы РСН среди них нет. В текстовый
  файл не пишутся таблицы РСН, РСУ, материалы и другие данные конструирования — они
  только в `.lir`. «Нормы таблицы РСУ» приходят из сопутствующего файла `.ald` ПК МОНОМАХ;
  его формат не описан.
- `ImportFile(Path, LirFileTemplate)`: с исходной моделью в роли шаблона ЛИРА отвечает
  «Ошибка» — шаблон не может содержать узлы, элементы и жёсткости.
- Очистить копию модели для шаблона из API не удалось: запись пустой таблицы ЛИРА
  игнорирует; команда `57632` (Del) после `Select("all")` ничего не удаляет; «Упаковка
  схемы» (`5089`) открывает диалог. Команды «удалить отмеченное» для схемы в меню нет.
- `GetParameters` у таблиц `LoadCases` и `DCL` возвращает пустое значение
  (`DISP_E_PARAMNOTFOUND`), `SetParameters` — «Несовпадение типов»: нормативный документ
  таблицы через API 2024 R2 не доступен.
- Не проверено: сохранит ли нормы импорт по пустому шаблону, сделанному вручную в окне
  ЛИРЫ (отметить всё, удалить, упаковать, сохранить).

Уточнение 2026-10-29 (пробы `t25_norms.py`, `t25_sp20.py`, `t25_restore.py`,
`t25_order.py`):

- Нормы по умолчанию — **СП 20.13330.2011/2016**: имя «Особое, Ps» есть только в их
  списке видов (справка, «Редактор загружений»). Нормы по умолчанию для новых задач
  настраиваются в «Параметрах расчётов при конструировании», так что на другой машине
  они могут быть другими.
- Текст хранит виды кодами в нумерации СНиП (0 Постоянное, 1 Длительное, 2
  Кратковременное, … 7 Мгновенное, 9 Неактивное), а импорт читает код как номер в
  списке СП 20. Поэтому пересборка путает виды и у моделей по СП 20: «Кратк. доминир.1
  ( Pt1)» → «Длит. прочие ( Pl)», «Неактивное (Н/а)» → «Прогрессирующее обрушение»,
  «Мгновенное(М)» → «Особое ( Ps)».
- Запись исходных строк `LoadCases` в пересобранную модель возвращает виды модели по
  СП 20 точно. У модели по СНиП (пример №1) — нет: «Длительное(Д)» становится
  «Постоянное ( P)», потому что в словаре СП 20 такого вида нет. Сервер теперь сравнивает
  виды после восстановления таблиц и отказывает только во втором случае.
- Учебные модели ЛИРЫ 2024 (32 модели): 5 по СП 20 (раздел 16, прогрессирующее
  обрушение), остальные по СНиП или без видов. Модели раздела 16 со стадиями монтажа
  пересборку не переживают: ЛИРА не принимает их `LoadCases` («Ошибка» при Apply), а
  `CollectionOfMasses` и `DCL` не восстанавливаются; при выгрузке текста одна из них
  спрашивает, заменить ли вид нелинейного расчёта «Монтаж».

## Находки T7 (2026-10-27)

- После окончания расчёта ЛИРА **закрывает документ** модели; для правки модель нужно
  открыть снова.
- Протокол расчёта — `<Work>/<имя>_01.<имя>` (UTF-8). Чистый расчёт заканчивается
  «Расчет успешно завершен», расчёт с проблемами — «Расчет завершен» и строки
  «ВНИМАНИЕ!!!» (например, геометрическая изменяемость). Код события
  `AnalysisFinished` в обоих случаях 0 — судить о проблемах можно только по протоколу.
- Во время расчёта ЛИРА пишет `<Data>/<имя>.txt` — текстовую копию модели.

## Находки T8 (2026-10-27)

- Библиотека результатов LiraResAPI читает файлы по **имени модели** (без пути) из папки
  Work, в своих единицах: м, рад, т, т·м. Перемещения без списка узлов и усилия без
  списка элементов возвращаются для всех.
- **Второй запрос через тот же объект `LiraResultsAccess` возвращает мусор** (числа
  порядка 1e-41). Для каждого запроса сервер создаёт новый объект — так значения верны.
- Число расчётных сечений стержня задаётся таблицей `Elements_DesignSectionsCount`
  (номер элемента, число сечений); по умолчанию 2 — начало и конец.
- Пример №1 (рама 6×3 м, 10 т/м): момент в ригеле −23,858 т·м на опорах и 21,142 т·м в
  пролёте, у основания колонн 11,575 т·м, продольная сила в колоннах −30 т — совпадает
  с расчётом методом перемещений.

## Находки T10: РСН и РСУ (2026-10-27)

- Если в модели нет РСН, запрос результатов РСН возвращает тот же код, что и при
  отсутствии расчёта (`E_UNEXPECTED`), — сервер различает их по виду запроса.
- Усилия РСН адресуются (элемент, сечение, номер РСН, предельное состояние 1–4);
  перемещения РСН — (узел, номер РСН). Сведения о РСН: имя, формула, особое,
  сейсмическое; нормы сочетаний модели 04 — СП (код 7).
- РСУ адресуются (элемент, сечение, предельное состояние, номер сочетания); для каждого
  есть критерий, группа (A1…E1), признак крана/сейсмики и состав загружений в нотации
  ЛИРЫ: «1-3,-4» — загружения 1–3 и 4 с обратным знаком.
- Таблицы ввода для РСУ в API 2024 R2 нет (есть только `DCL` для РСН).

## Находки T11: динамика, арматура (2026-10-27)

- Подобранная арматура: каждый метод возвращает пару (значение, код ошибки); 0 — норма,
  200 — не вычислялось, −1 — сечение недостаточно, −71 и −67 — предупреждения при
  выданном значении. Работает только этап монтажа 0 (1 — ошибка) для модели без
  монтажа. У стержней два варианта — несимметричное и симметричное армирование; не
  подобранный вариант читается нулями с кодом трещин 200.
- Номер варианта конструирования задаётся в запросе (`DesignOption`); в модели 02 их два.
- Периоды: массивы по каждому динамическому загружению; модальные массы — в процентах.
- Нагрузки на фрагмент и на контуры продавливания в учебных моделях не заданы: запрос
  возвращает код «нет результатов».
- Нагрузки на фрагмент проверены 2026-10-30 на модели владельца (фрагмент из 5 узлов,
  10 статических загружений, сейсмика с формами 13, 15–18, 25; пробы
  `spikes/t_frag_punch.py`, `t_frag_punch2.py`). Компоненты 1–6 — RX, RY, RZ, RUX, RUY,
  RUZ, как в `LiraFragmLoadForceEnum`; бимомента (7) в ответе нет. Значения — в тс и
  тс·м: умноженные на 9,81 они совпадают с собственной таблицей ЛИРЫ «Нагрузки на
  фрагмент» (CSV, `kLiraCsvTable_Load_fragment` = 26, включается
  `SetGenerateCsvTables`), включая знаки. Форма динамики здесь задаётся **номером формы
  колебаний** (13, 15…), как в перемещениях, а не порядковым номером, как в усилиях:
  1–7 — ошибка. Суммарная форма — тоже −1, по модулю равна корню из суммы квадратов форм.
  Таблица ЛИРЫ печатает 6 значащих цифр и очень малые значения (около 0,001) пишет нулём.
- Нагрузки на контуры продавливания (та же модель, контур вокруг узла 315; пробы
  `spikes/t_punch3.py`–`t_punch5.py`). Расчёт, запущенный через API, их не создаёт:
  запрос отвечает «нет результатов», таблица ЛИРЫ 44 не пишется, даже если её включить.

  материалы B35, A500C). Ответ содержит все узлы модели (7961) с нулями вне контуров —
  чтение всех 135 тыс. строк занимает ~1 с. Компоненты 1–6 — N, MX, MY, QX, QY, MZ;
  значения в узле 315 совпали с концевыми усилиями колонны 13, которая приходит в этот
  узел: N = N, MX = −Mz, MY = My (оси разные), QX и QY — нули. Формы сейсмики —
  номером формы, как у фрагмента; суммарная −1 — корень из суммы квадратов.
- Проверку продавливания можно запустить через API: `StartCmd(49595)` — пункт меню

  диалогов (`spikes/t_punch_run.py`, `t_punch_edge.py`). Модель должна быть открыта и
  активна: после расчёта ЛИРА её закрывает.
- Новый расчёт **не удаляет** файл нагрузок `#62` прежней проверки: запрос нагрузок на
  контуры отдаёт старые значения. Устаревшие нагрузки узнаются по времени: протокол

  старше протокола — от проверки до последнего расчёта.

## Импорт текста и рабочие файлы ЛИРЫ (2026-10-30)

- `ImportFile` текстовой модели берёт данные, которых нет в тексте, из рабочих файлов
  ЛИРЫ (`<имя>#07.<имя>` и подобных в рабочей папке) рассчитанной ранее модели с тем же
  именем: новая модель получила kE = 2 всех элементов от старой одноимённой. Без
  расчёта (рабочих файлов нет) этого не происходит. Проба `spikes/t_ke_factor.py`.

  что унаследованные данные не проходят незамеченными.
- kE (`Stiffnesses_Factors`) умножает модуль упругости элемента; частичная запись
  (`numbers`) тоже действует (`spikes/t_ke_partial.py`).

## Стадии монтажа, коэффициенты РСН и сопутствующие файлы (2026-10-31)

Пробы `spikes/t_stages_cases.py`, `t_stages_text.py`, `t_stages_companions.py`,
`t_stages_rebuild.py`, `t_dcl_write.py`, `t_dcl_doc8.py`, `t_doc8_codes.py`,
`t_ald_norms.py`, `t_stages_full.py` на копиях примеров 1, 7, 16, 18.

- **Откуда лишние загружения.** Документ 16 текста — история нелинейных загружений
  («Монтаж»): строка на загружение. У примера 16 в истории загружения 1–5. Запись
  таблицы `AssemblageStages` в модель, где стадий не было, дописывает в конец истории по
  загружению на каждую стадию, номерами после последнего в истории, и создаёт
  недостающие («Загружение 7» …). Итого загружений — длина истории + число стадий: 5
  стадий дают 6…10 (создаются 7–10), 2 стадии — 6…7 (создаётся 7), а если загружений
  уже 9 — создаётся только 10. Повторная запись тех же стадий в исходную модель ничего не
  добавляет.
- **Сопутствующие файлы.** Выгрузка в текст пишет `<имя>.mnt` в папку данных (стадии:
  `( 1 / 1 ; 1 3 5 11-18 / )`) и `<имя>.ald` в рабочую папку (XML: плотность `Ro`,
  цвет и комментарий жёсткостей, `RsuCodeData RsuCodeIndex` — нормы РСУ, конструктивные
  блоки). Документ 0 ссылается на `.mnt` строкой `40;"<имя>.mnt"`. Импорт читает файлы,
  лежащие рядом с текстом под именем самого текстового файла (не модели), и спрашивает
  «В каталоге импорта содержится файл монтажных таблиц… импортировать эти таблицы?»;
  ответ «Да» возвращает стадии и блоки без записи таблиц — история не растёт.
- **Имя файла стадий у модели со скобками** (`spikes/t_mnt_braces.py`, 2026-11-01).
  Модель `m(v1)` выгружается со строкой `40;"m{v1}.mnt"` и файлом `m{v1}.mnt` в папке
  данных: круглые скобки ЛИРА заменяет фигурными (у владельца так названы
  `157_k1{e03_06}_v3.mnt` и другие). Импорт текста `m(v1).txt` читает только
  `m(v1).mnt` — со скобками как у текста; файл `m{v1}.mnt` рядом он не видит, и стадии
  пропадают. Сервер берёт файл по строке 40 и кладёт рядом с текстом под именем текста.
- **Нормы из `.ald` импорт не применяет.** `RsuCodeIndex` у примеров на СНиП — 0, у
  примера 16 — 2; модель, импортированная с `.ald` примера 1, всё равно получает виды
  загружений по СП 20.
- **Коэффициенты РСН.** Запись таблицы `DCL` ЛИРА молча игнорирует: γf, доля

  строки заголовка — «Неверное значение»). γf сбрасывается к значению по виду, когда

  взаимоисключения несёт документ 8 текста (таблица РСУ): строка

  «физ_нелин» его нет). Документ 8, составленный из таблиц исходной модели и добавленный
  в текст перед импортом, даёт верные γf; запись `LoadCases` с теми же видами их не
  сбрасывает; при выгрузке пересобранной модели документа 8 снова нет.
- **Коды видов документа 8 по СП 20:** 0 «Постоянное ( P)», 1 «Длит. доминир.1 ( Pl1)»,
  2 «Длит. прочие ( Pl)», 3 «Кратк. доминир.1 ( Pt1)», 4 «Кратк. доминир.2 ( Pt2)»,

## Строки 50 и 51, арматура и вопрос «Монтаж» (2026-10-31)

Пробы `spikes/t_entries_50_51.py`, `t_rebuild_steps.py`, `t_nsag_import.py`,

- **Строки 50 и 51 документа 0.** В `LiraSapr.exe` их формат — `50; %d /` и `51; %d /`

  сохраняет 0, если они записаны явно (примеры 1 и 7). Сервер дописывает `50; 0` и
  `51; 0` в текст перед импортом, когда их нет, и сверка текста их больше не прощает.
  Что эти параметры значат, не выяснено.

  стадий и динамику во времени (разрушено 21 элемент против 22).

## Пластины в текстовом формате и узлы четырёхугольников (этап 6, 2026-11-03)

- Жёсткость пластины в документе 3: `1 GEI E ν h RO γ/` — E в т/м², толщина h в
  метрах, удельный вес γ в т/м³ (пример 02: `1 GEI 3e+006 0.2 0.15 RO 2.75 /`).
- Равномерная нагрузка на пластину в документе 6 — тип 16: `элемент 16 3 строка
  загружение/`, первое значение строки документа 7 — давление (т/м²).
- Узлы четырёхугольной пластины ЛИРА перечисляет **крест-накрест**: два узла одной
  стороны, затем два узла противоположной в том же направлении (`1 2 8 9` у КЭ 11
  примера 02) — и в тексте, и в таблице `Elements_TypeAndNodes`. Текст с узлами по
  обходу контура ЛИРА принимает, но расчёт отказывает: «У элемента №… некорректная
  геометрия» (КЭ 44, проба `spikes/t6_slab_model.py`). Постобработка поэтому
  упорядочивает узлы пластины по углу вокруг её центра.
- Перемещения узлов читаются только по Z (`vertical_displacements`): у плиты в десятки
  тысяч узлов это в шесть раз меньше вызовов COM, чем все шесть направлений.
- **`NodeNumbers.AddToString` на разрозненных номерах роняет процесс.** Порча кучи
  (0xC0000374) в библиотеке результатов, гибнет весь процесс сервера. На модели владельца
  (228 тыс. узлов) проба случайных номеров: 1000 проходят, 3000 падают; сплошной диапазон
  всех узлов проходит. Первая версия обхода (части по 5000 номеров) работала на плитах
  только потому, что их номера идут почти подряд. Причина снята: номера читаются через
  `Count` и `Item` (индекс с нуля, на 800 номерах совпало с `AddToString`). После этого
  30 000 разрозненных узлов проходят и одним запросом (55 с), и частями (40 с).
- **Имя модели без `. # * ? ,`.** `OpenDocument` файла `m_kE0.5.lir` показывает окно
  «Символы ' . ' ' # ' ' * ' ' ? ' ' , ' не разрешены в имени задачи» с кнопкой «ОК»
  (кириллица) и ждёт ответа. Сервер отказывает в таком имени до вызова ЛИРЫ (открытие,
  «сохранить как», копия с трещинами пишет `_kE0_5`); кнопки окон сравниваются с
  заменой похожих кириллических букв на латинские, так что «OK» нажимает «ОК»
  (проба `spikes/t6_dot_name.py`).
- Результаты расчёта переживают чтение таблицы ввода модели (флаг «изменена»),
  сохранение, закрытие и повторное открытие (проба `spikes/t6_results_kept.py`). После
  расчёта ЛИРА сама закрывает модель.
- Результаты копии модели владельца `lmcp_157-…` (расчёт 57 мин) пропали из папки Work
  после прогона живых тестов другой сессией: уборка тестов (`tests/live/conftest.py`)
  удаляла все файлы `lmcp_*` в папках ЛИРЫ. Теперь она удаляет только появившиеся за
  прогон (571c41b); пробы на больших моделях всё равно называют копии без `lmcp_`.
- Коэффициенты сочетаний РСН API не отдаёт (`DCL` хранит по загружениям вид, знак, γf и
  долю длительной). Нормативное длительное РСН находится подбором: перемещения узлов по
  РСН — сумма перемещений загружений с искомыми коэффициентами (метод наименьших
  квадратов, `spikes/t6_owner_combos.py`). На модели владельца (23 РСН, 400 узлов)
  невязка ~1e-16: перемещения РСН ЛИРА отдаёт как сумму с коэффициентами
  «коэффициент сочетания / γf». РСН 3 — нормативное длительное: постоянные и длительные
  1/γf, кратковременные «доля длительной / γf» (полезная 0,35/1,2, снег 0,5/1,4),
  особых нет. Загружения стадий монтажа 1–4 отдельных результатов не имеют: их вклад —
  в загружении последней стадии.

## Жёсткость одноузловых элементов (2026-11-07)

- КЭ 56: номер в `Elements_Stiffnesses`, код 55 в `Stiffnesses`, параметры
  `Rx:200 Ry:200 Rz:0 Rux:0 Ruy:0 Ruz:0 DD56_END`. В тексте модели — строка раздела 3 `4 200 200 0 0 0 0 /`; импорт такой
  строки восстанавливает те же параметры. В примерах №09 и №11 у всех элементов КЭ 56 `Rz:0`.
- КЭ 57: номер жёсткости в `Elements_Stiffnesses` равен 0 (примеры №15, №22, модель владельца). Жёсткость сваи хранится
  не в `Stiffnesses`.
- КЭ 51 в примерах ЛИРЫ не встречается. Запись в тексте — строка раздела 3 `2 3 1000/`: направление, затем жёсткость;
  ЛИРА читает её как код 17 с параметрами `EF:1000 n:3 DD51_END`. Варианты `2 1000/`, `2 1000 3/`, `2 0 0 1000/`,
  `2 0 0 1000 0 0 0/`, `2 KZ 1000/` и запись КЭ 56 импорт принимает молча, но у элемента остаётся номер жёсткости 0.
  Запись строки с кодом 17 и параметрами `Rz:1000` в `Stiffnesses` ЛИРА отклонила («Неверный индекс»).
- Запись нелинейных аналогов (КЭ 251, 252 и другие) не проверялась.
